## 5. Martingale history
- 2026-07-31 stale-target bug (PR #40 d9f7037): an absolute TP + `repeat` → every round after 1 keeps aiming at round 1's price while the ladder re-anchors; the live demo case ended with a "take profit" BELOW the round's own realised average. Symptom = re-asking the venue for the stop every ~6s and paging each time; underneath, once price fell through the stale target the venue refused the stop outright — and since the exchange-side TP is a round's ONLY exit, **the round could not close at all**. Fixes: take_profit_pct (fraction of the round's own anchor, recomputed each round); a tp_through_market error kind that closes the round with a reduce-only marketable limit ("fills at the target or better, never worse"; not post-only — a marketable post-only is rejected); config refuses the absolute TP alongside repeat.
- The round-2 TP has NEVER been observed on fixed code (needs a modest price move that hasn't occurred); the pre-fix bug IS captured in the demo log (rounds 2-6 all set the identical stale target while each re-anchored to a different mark).
- Restart-flattens-a-round (8c9f796): round state is memory-only → a restart rewinds the anchor to the config entry and round 1, then rewrites a live TP off its round; if price had already run through the recomputed level, tp_through_market fires and the whole round closes at market — **an unplanned exit caused by nothing but a restart**. A real demo restart rewound two live martingale rounds; harmless only because both happened to be in round 1. Fix = adopt the resting TP on the first cycle found holding (believe the exchange; one-shot; specs pin no-write-on-restart, adoption announced, adopted round still loops, and a holding round with NO exchange TP still gets one). The round counter in notifications still restarts at 1 — cosmetic.
- Test-2: the martingale originally had no re-arm suppression at all (accumulated well past its ladder cap while price sat pinned) → suppressed once the position covers the cumulative ladder through a level (0350ccf).
- The martingale budget is the whole ladder's, normalised across level_weights — not per step.
- A deliberately-tight stress pair was added 2026-08-01 to hunt: the round-2 TP on fixed code, the tp_through_market path, round-state under rapid re-anchoring, and the restart adoption path. Economics deliberately ~break-even: "this earns nothing and is not meant to."

## 8. Ops constraints bearing on v3 (identifiers redacted)
- Deploy: a VPS running the fleet as a systemd --user service; four layers (Restart=always; OnFailure deterministic Telegram alert; a read-only headless triage script — read-only enforced by settings, not trust; an output watchdog on a timer for the wedged-but-alive case). Two fleets share one small box; the demo unit must never carry --allow-mainnet; the watchdog timers are offset so the mainnet tick never queues behind the demo one.
- No hot reload: "live-modify" = edit the file and restart; the restart being non-destructive is the actual feature. Runbook: workstation on dev → dry-run → backtest → ADD THE BOTID TO THE WATCHDOG CONFIG (or it is unwatched) → re-derive the equity floor → suite green → PR → owner merges → VPS pull + restart. A pull alone changes nothing until restart. Never edit on the VPS.
- **ONE fleet process per account, ever** (two HL signers collide on nonces); the handover is stop+disable the old process FIRST; resting orders survive the gap and re-adopt by identity — minutes of downtime are safe and expected.
- --cleanup is test-only (on a real fleet it would tear down a live ladder every restart); Ctrl+C leaves orders resting. Maintenance: stop the watchdog timer first ("a stopped fleet is indistinguishable from a wedged one — by design").
- Watchdog: thresholds measured from snapshot telemetry with explicit headroom multiples; **every threshold assumes the grid is the only actor on the account — a manual position can move equity and margin more than the grid can, so a page may be reporting the operator's own trade** (this forced one ceiling to be re-derived upward). A withdrawal reads as drawdown forever (the peak is monotone): drop the peak, re-derive the floor, re-derive the budget. Every bot must appear in its fleet's watchdog config (the spec fails both ways); position ceilings are pinned to the cap ×1.2 so a breach means the cap itself failed. "Prose rots; an assertion fails loudly."
- Inbound control: a relay on a timer, one-sender fail-closed, addressed-to-us only, persist-before-ack (a crash costs a duplicate, not a lost instruction), structurally unable to write; a standing brief outside git so headless answers don't mistake designed behaviour for a fault; nothing else may poll the same Telegram queue.
- Process failures worth carrying: **real position sizes were once pushed while a repo was public — "a commit is a publication"**; a PR was reported merged while still open (verify merged=true from the API); the suite-green-at-merge rule was broken twice, both times by a config change.
